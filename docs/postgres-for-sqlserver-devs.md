# Postgres for SQL Server Developers

You already know SQL Server. This guide maps what you know to Postgres, so you can read the code in this repo without re-learning databases from scratch. The full comparison lives in the `sqlserver-efcore-pro` repo — this one is the Postgres side.

## The 60-second version

| SQL Server | Postgres | Notes |
|---|---|---|
| `IDENTITY(1,1)` | `GENERATED BY DEFAULT AS IDENTITY` | EF Core generates this for `int` keys on both |
| `GETDATE()` / `SYSDATETIME()` | `now()` | `now()` is transaction-start time, not wall-clock time |
| `TOP 10` | `LIMIT 10` | Postgres also has `OFFSET`, same idea |
| `NVARCHAR` | `text` / `varchar(n)` | Postgres `text` has no length penalty — use it unless a limit matters |
| `DATETIME2` | `timestamp` / `timestamptz` | EF Core maps `DateTime` to `timestamptz` on Postgres — always UTC |
| `BIT` | `boolean` | `true`/`false`, no 0/1 confusion |
| `UNIQUEIDENTIFIER` | `uuid` | `gen_random_uuid()` instead of `NEWID()` |
| `MONEY` | `numeric(10,2)` | Never use `money` on either side; `numeric` is exact |
| `VARBINARY(MAX)` | `bytea` | Same idea, different name |
| `XML` | `xml` / `jsonb` | Postgres has both; `jsonb` is the one you will actually use |
| `TRY_CAST` | `x::type` / `CAST(x AS type)` | The `::` cast operator is everywhere in Postgres SQL |

## Identity columns

SQL Server: `IDENTITY(1,1)` auto-increments and you mostly forget about it.

Postgres: `GENERATED BY DEFAULT AS IDENTITY` — same behaviour, and EF Core's Npgsql provider generates it for integer keys automatically. The older `SERIAL` type still works but is legacy; prefer identity columns.

One difference that bites: Postgres sequences are **not transactional**. A rolled-back insert still burns the sequence value, so ids have gaps. That is normal — never assume ids are gapless on either database.

## Dates and times

- `timestamp with time zone` (`timestamptz`) is the default for .NET `DateTime` on Postgres. It stores UTC and converts on read using the session timezone. Store UTC, always.
- `now()` returns the **transaction start time**, so every `now()` call inside one transaction returns the same value. That is a feature (consistent timestamps), not a bug. For wall-clock time use `clock_timestamp()`.
- `CreatedUtc` in this repo uses `HasDefaultValueSql("now()")` — the database stamps the row, not the application.

## Strings: `text` has no penalty

On SQL Server, `VARCHAR(MAX)` vs `VARCHAR(100)` is a real decision. On Postgres, `text` and `varchar(n)` perform identically — the length limit is only a constraint. This repo uses `text` for descriptions and `varchar(32)` for SKU where the limit is a business rule.

## What Postgres has that SQL Server doesn't (used in this repo)

- **Arrays as a column type.** `Tags text[]` stores a list in one column. Query it with `@>` (contains) and `&&` (overlaps). This is not a normalized design — it is a deliberate choice for data that is only ever read as a set.
- **JSONB.** A binary JSON column you can index and query. `Specs ->> 'color'` reads one key; `Specs @> '{"color": "black"}'` tests containment. See `docs/jsonb-and-full-text-search.md`.
- **Full-text search built in.** `to_tsvector` / `to_tsquery` / `ts_rank` with GIN indexes. No separate search service for most catalog search.
- **Advisory locks.** `pg_advisory_xact_lock(bigint)` is a named mutex in the database — no table, no row, released automatically at transaction end. This repo uses it for idempotent orders.
- **LISTEN/NOTIFY.** The database can push events to a connected client. No polling, no queue. This repo uses it to broadcast product changes.
- **Generated columns and exclusion constraints, CTEs that can UPDATE/DELETE** (`WITH ... UPDATE ... RETURNING`), and `RETURNING` on every DML statement — `INSERT ... RETURNING id` replaces `SCOPE_IDENTITY()`.

## What SQL Server has that Postgres doesn't

- **No `MERGE` with the same semantics** — Postgres has `INSERT ... ON CONFLICT DO UPDATE` (upsert), which covers the common case more simply.
- **No built-in Agent / SQL Agent jobs** — scheduling lives outside the database (Quartz.NET, pg_cron extension, or a worker). See the `dotnet-background-jobs` repo.
- **No `CROSS APPLY` syntax** — `LATERAL` joins are the equivalent.
- **No clustered indexes as a concept** — Postgres tables are heaps; the `CLUSTER` command physically reorders once but is not maintained.
- **Temp tables behave differently** — `#temp` tables in SQL Server vs `TEMP TABLE` in Postgres; Postgres temp tables are per-session and dropped automatically.

## EF Core provider differences

| Area | SQL Server provider | Npgsql provider |
|---|---|---|
| Provider package | `Microsoft.EntityFrameworkCore.SqlServer` | `Npgsql.EntityFrameworkCore.PostgreSQL` |
| Migrations | `dotnet ef migrations add` | Same commands, same workflow |
| HiLo / sequences | `UseHiLo()` | Identity columns by default |
| `string` length | `nvarchar(max)` by default | `text` by default |
| Case sensitivity | Case-insensitive by default (collation) | **Case-sensitive by default** — `WHERE Name = 'abc'` won't match `'ABC'`; use `EF.Functions.ILike()` or `citext` |
| `DateTime` mapping | `datetime2` | `timestamptz` |
| JSON columns | `json` (SQL Server 2022) | `jsonb`, with real operators |

The case-sensitivity row is the one that surprises people. Postgres string comparison is case-sensitive unless you ask otherwise. For user-facing search, either lowercase both sides or use `ILIKE` / `EF.Functions.ILike()`.

## When to pick which

- **Postgres:** JSONB-heavy models, full-text search without a search service, arrays, geospatial (PostGIS), or when you want one database that does many jobs well.
- **SQL Server:** existing Microsoft estate, T-SQL stored-procedure culture, Always On availability groups, or when the client standardizes on it.

Both are excellent. The skill is knowing which tool the job needs — and this repo exists so Postgres is a tool you can actually reach for.
